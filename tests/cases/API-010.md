# API-010 — Rate limit tải lên → 429 + Retry-After

| Thuộc tính | Giá trị |
|---|---|
| **ID** | API-010 |
| **Loại** | API black-box |
| **Ưu tiên** | P1 |
| **Truy vết** | API Design 2.3 · API-010 · SEC-013 |
| **URL kiểm thử** | http://127.0.0.1:8000 |
| **Thư mục artifact** | `tests/reports/API-010/` |
| **Nguồn** | [docs/testing/Test_Plan.md](../../docs/testing/Test_Plan.md) |

## Mục tiêu

Vượt hạn mức tải lên (thiết kế: 20 lượt/giờ/người dùng) trả `429 RATE_LIMITED` kèm `Retry-After`.

## Điều kiện tiên quyết

- Máy chủ đang chạy tại http://127.0.0.1:8000 (`GET /health` → 200; devserver: adapter LLM/embedding giả, dữ liệu trong bộ nhớ).
- Tài khoản dev **mới, tên duy nhất** cho case này (vd `tc<mã-thời-gian>`), tạo bằng `tc.apiLogin()` hoặc form đăng nhập.
- Tài khoản đã xác nhận thông báo dữ liệu (`GET /api/v1/data-notice` → lấy `version` → `POST /api/v1/data-notice/acceptances`) — với UI dùng `tc.acceptNotice()`.

## Các bước và kết quả mong đợi

| # | Hành động | Kết quả mong đợi |
|---|---|---|
| 1 | Gửi liên tiếp các yêu cầu tải PDF nhỏ (mỗi lần `Idempotency-Key` mới) | Các lượt đầu `202` |
| 2 | Tiếp tục tới khi gặp lỗi | Có phản hồi `429`, `code=RATE_LIMITED`, header `Retry-After` > 0; ghi lại số lượt thực tế trước khi bị chặn |
| 3 | Gọi `GET /documents` bằng cùng token | Vẫn `200` (chỉ endpoint bị giới hạn bị chặn) |
| 4 | Dùng tài khoản khác tải 1 tệp | `202` (giới hạn theo người dùng) |

## Tiêu chí đạt

Tất cả các bước đều đạt kết quả mong đợi. Bất kỳ bước nào lệch → case **FAIL**.

## Lưu ý

- Nếu số lượt thực tế khác 20, ghi nhận lệch so với đề xuất (`[Đề xuất]`, OQ-011).

## Nhiệm vụ của agent

Bạn là agent thực thi test case này. **Phải** tạo đủ các artifact sau trong thư mục riêng `tests/reports/API-010/`:

| Artifact | Đường dẫn | Yêu cầu |
|---|---|---|
| Test report | `tests/reports/API-010/report.md` | Kết quả tổng, từng bước (mong đợi vs thực tế), lỗi phát hiện, ghi chú |
| Ảnh chụp màn hình | `tests/reports/API-010/screenshots/*.png` | Ít nhất **một ảnh cho mỗi bước** (khung tự chụp); ảnh bước lỗi có tiền tố `fail-` |
| Video | `tests/reports/API-010/video/API-010.webm` | Quay toàn bộ quá trình chạy (khung tự quay) |
| Kết quả máy đọc | `tests/reports/API-010/result.json` | Tự sinh |
| Mã chạy | `tests/reports/API-010/run.mjs` | Script bạn viết để thực thi case này (giữ lại để chạy lại) |

**Quy trình:**
1. Đọc [tests/README.md](../README.md) (cách dùng khung `tests/tools/tc.mjs`: `startCase`, `tc.step`, `tc.http`, `tc.login`, `tc.axe`…).
2. Xác nhận máy chủ `http://127.0.0.1:8000/health` trả `200`. Nếu chưa chạy, khởi động theo README (không đổi mã sản phẩm).
3. Viết `tests/reports/API-010/run.mjs` dùng `startCase("API-010", { title: "…" })`. **Mỗi dòng ở bảng “Các bước” là một `tc.step(tên, mong_đợi, fn)`**; dùng `expect` để kiểm tra, trả về chuỗi mô tả kết quả thực tế. Case API dùng `tc.http()` để mỗi request/response có ảnh bằng chứng; case UI dùng ảnh chụp giao diện.
4. Chạy `node tests/reports/API-010/run.mjs` từ thư mục gốc repo; mở vài ảnh chính để chắc chắn chúng thật sự là bằng chứng của bước đó.
5. Phân loại kết quả trung thực:
   - Sản phẩm sai so với “Kết quả mong đợi” → giữ **FAIL**, ghi `tc.defect("mô tả + cách tái hiện + mức độ")`. **Không** sửa mã sản phẩm, **không** nới kỳ vọng để “cho đạt”.
   - Lỗi do script/selector của bạn → sửa script và chạy lại.
   - Không thể kiểm chứng (thiếu môi trường, ngoài khả năng của devserver) → ghi rõ trong `tc.note(...)` và trong kết luận là **chưa kiểm chứng** (không ghi PASS).
6. Dọn dẹp trạng thái dùng chung (ví dụ bật lại kill switch) trong `finally`.
7. Kết thúc bằng một câu trả lời ngắn: **ID · PASS/FAIL/chưa kiểm chứng · đường dẫn `report.md` · lỗi phát hiện (nếu có)**.

**Tiêu chí hoàn thành artifact:** `report.md`, ≥ 1 ảnh mỗi bước, 1 video `.webm` không rỗng và `result.json` đều tồn tại; report không chứa token/secret/nội dung nhạy cảm.
